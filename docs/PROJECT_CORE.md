更新：2026-11-06。用户已授权 SullyOS 模块接入与规则内核验证；实验范围、复用文件、复现入口和结果见 [WORLD_PROBE.md](WORLD_PROBE.md)。本文件是当前工作区的长期维护原件；AGENTS.md、README 均已接入。

## 最新确认与本次实验

- 已确认：手机本机运行、后台间歇推进，中断后按规则补算和生成；暂不引入常驻服务器。以后通过实际体验决定是否更换持续运行宿主。
- 优先验证 SullyOS 产品模块、float 的预设/动作/应用能力与 T 的 Android 运行基础能否组合，不预先锁定最终产品底座。
- 代码优先取用既有项目，记录实际保留段及外部适配；“参考设计后另写同类实现”不能当成代码复用。
- 本次仅 debug 实验：SullyOS 原始 threads.ts、A-Life 原始 Clock/GOAP 由 QuickJS 执行。使用隔离数据库，不迁移或读取用户聊天/主记忆，不调用模型，不发布 APK 更新。
- A-Life 原始时钟单次跨 48 小时会遗漏小时回调；保留原码，在外部按小时分段推进。积温只列唤醒候选，urbe-population 因 UNLICENSED 排除导入。
- 该实验不验证完整家园引擎、自然后台准时运行或真实模型效果。手机产品界面、世界规则与数据底座的最终组合仍要按更完整模块验证。

## 2. 已确认的愿景与原则

- 用户选择 C：持续存在的世界，加上独立自主的人物。世界有用户不参与也会发生的活动与关系；用户可以是过路人、邻居或其他相遇者，不默认成为人物生活的中心。
- 人物需要可执行的生活权利：自主交流、联系、串门、写信、建造家具、更衣和动作，以及自己的手机。用户希望有相册和可安装的应用。以上是目标，不代表已实现。
- 不让大模型每几秒轮询下一步。确定性日常由程序规则执行；未定状态可用概率或随机“塔罗牌”衍生；重要决策才唤醒相应人物调用模型。
- 每次代码行动优先取用现有项目代码。先检索本项目、用户已有仓库及 awesome-ai-companion，逐文件确认可用性，再决定适配。只借鉴设计却重写同类代码，不能算完成了复用要求。
- 模型提出意图与表达，世界规则验证并提交行动。人物陈述、主观理解、世界事实分别保存。未知设定不补造。
- 虚构剧情独立保存；用户选择的内容才能按已确认流程转入指定人物记忆。读入记忆不等于允许自动写回；故事不覆盖持续世界的当前事实。
- 当前授权：执行用户已确认的隔离集成实验、必要适配与文档；产品迁移和公开试用发布不在本次范围。

## 4. 既有成果与底座选择

已存在可独立于聊天使用的世界命令、事件与知情校验：frontend/world-core.js；已有无 DOM 的居民任务状态机：resident-life-core.js；已有主动投递：proactive-messages.js。Android 已经用 QuickJS 执行共用规则，TDocumentStore 的 CAS/租约保护前后台写入，TResidentWorker 用 WorkManager 唤起。名册、记忆、模型连接与本机存储也已有明确入口。这些是可以继续使用的基础。

主要差距在生活运行方式，而不是缺少一套聊天产品。resident-life-core 的 beginLifeRun 要求恰好两位居民，nextLifeJob 用 cursor % 2 轮转，日常 action 进入模型任务；resident-life-service 对 prepared 任务先请求 auxiliary，再接受响应。world-map 固定 12×13 单房间与家具。现状是有限居民批次，不是按日程、物品和社会关系持续运转的通用世界。

更换产品底座需要承担人物/记忆/聊天数据迁移、Android 存储与后台执行适配，以及现有衣柜与更新渠道集成；继续全用 T 则需要迁入用户喜欢的界面、剧情和应用生态。SullyOS 已有家园按时段补触发、角色间线程和逐角色演绎；float 已有应用安装/运行与插件链路。优先验证这些实际模块的组合，不能再只把它们列成设计参考后自行重写。

本次通信模块实验通过，只支持继续做模块级组合验证，尚不足以证明完整 SullyOS 界面、记忆数据库和世界引擎可直接迁入。保留有价值的 T 模块；最终产品底座依据后续成组模块兼容和迁移成本决定。

## 5. 模块处置与风险

| 模块 | 处置建议 | 原因与主要风险 |
|---|---|---|
| 人物 ID、Canon/Persona、模型连接、原生传输、SSE、备份与更新 | 保留复用 | 连续身份及已有数据的基础；不因运行机制改变而迁移人物 |
| 记忆、来源版本、OB/词法召回、0.22 消化 | 在集成候选上复用，按需要扩展 | OB 为派生缓存；不并排引入另一份权威人物记忆；先接续已有手机验收 |
| 衣柜、形象、绘制与动作资源 | 复用 0.24 工作区 | 已有来源清单；更衣状态进入世界规则，表现资源不拥有生活决策 |
| world-core、事件、知情与行动校验 | 保留接口原则，扩展实现 | 从单房间两人扩展到地点、物品、占用和多人物；数据迁移与历史可读性风险高 |
| resident-life-core 的任务恢复/额度/去重 | 复用 | prepared/requesting/responded/applied 已处理重复执行与不确定请求 |
| “下一日常动作先请求模型”的决策路径 | 局部替换/重构 | 改成规则推进和重要事件唤醒；不丢失原恢复与预算保障 |
| WorkManager、QuickJS、SQLite CAS | 保留宿主，调整调度接口 | 原生执行可复用；当前居民批次持租约到有限执行结束，扩大人物数量会加重串行等待 |
| LocalService、app.js | 收敛编排，暂不全量重写 UI | 避免新增生活逻辑继续堆入总入口；页面只发命令、读快照 |
| 电话、信件、相册、可安装应用、家具制作 | 先查现成模块后适配 | 尚不能把桌面图标视为应用生态；需物品/通信/权限接口，复杂度高 |

这里的“重构/重写”是处置范围，不授权从零造轮子。只有现成实现不适用且原因写清后，才补最小适配和缺失规则。

## 6. 建议的目标运行机制

世界时间/到期事件 → 规则推进已有活动 → 校验并提交世界变化 → 判断是否需要唤醒人物 → 必要时调用模型提出意图 → 执行动作并保存事件 → 按知情范围供记忆与通信读取。

生活调度模块管理到期队列、去重、取消、恢复和预算；世界模块拥有地点、物品、实际行动与事件；人物模块拥有身份；个人认知模块拥有主观理解；通信模块拥有实际送达与未读；渲染只读取状态。它们通过少量命令和查询接口协作，不各建一份可独立编辑的“当前事实”。

确定性活动可记录开始、预计结束、目标和所需资源；程序处理走路、完成作息、占用冲突等。计划被打断、重要关系事件、陌生情况或重大选择再唤醒人物。模型可决定暂不联系用户。

随机/塔罗是受约束的不确定性输入：抽取一次并保存结果、规则版本及对应事件；重开页面和重试不能重抽。同样的结果对不同人物可以产生不同候选，不得直接变成“某人已经爱上某人”之类的事实。可先由规则解释；需要角色判断时才交模型。

已选择手机本机间歇推进与离线补算。当前 Android 后台不能保证关机、强制停止时继续执行；补算应记录区间与模拟时间。未来如果更换常驻宿主，再设计权威世界迁移和多端写入；现有共同后端不是本机世界的自动同步主脑。

- SullyOS：固定 8035795e443579ead0f28d1dfe9d5a87ff0b232e，本轮直接读取 docs/memory-system-overview.md，blob e84aeb89d11589fc9872ce4c65c05f5ea01f4e17。文档明确区分传统归档与宫殿，描述批次成功后推进水位。剧情组件候选及既有授权记录见 STORY_MEMORY_EXECUTION_PLAN、THIRD_PARTY_NOTICES；个人二改授权与公开分发范围逐文件核对。

- 衣柜：config/wardrobe-studio-sources.json 已记录 LPC、Fashion Sense 等来源，继续使用已有集成，不重复导入。

每次代码行动记录：需求 → 检索范围 → 仓库/固定提交/文件/blob → 实际复用段 → 许可证及保留署名 → 依赖与适配 → 排除候选的理由 → 验证。能直接复用的先复用；找不到时明确说明检索结果，只补必要缺口。

## 8. 建议实施顺序与可观察验收

1. 确认集成基线及已有 3A/衣柜验收，保护全部现成功能与数据。不要在旧文档分支再做一遍记忆。
2. 做一个两人物、少量活动的规则生活闭环：用户不发消息时活动可开始/完成；普通活动不调用模型；重要事件只产生一次唤醒；重启不重复行动、不重复投递或计费。
3. 扩展多人物、多地点、物品占用和角色间通信，验证人物只知道实际可知事件。用户长期离开也有与用户无关的变化。
4. 再接电话/信件/相册/应用与更复杂制作，按模块取用现成实现；持续世界和虚构剧情保持既有流转约定。

阶段验收要记录规则推进次数、模型请求次数与原因、事件来源和恢复结果。费用与容量通过小样本测量后再估算，不在本轮给没有依据的工期。
