## 当前结论

**直接把原 `T-` 仓库切成公开：NO-GO。** 原因是已确认的历史邮箱、平台元数据、历史 LAN 地址，以及尚未逐项复核的旧日志/产物。删除最新文件、改 `.gitignore` 或只改最新作者邮箱都不够。

推荐的可评审方案：从本次审核后的源码生成干净快照，以 noreply 身份创建新的起点；原仓库继续私有保存历史与旧 PR。新的公开仓库只接收清理后的源码和后续正常 PR，不携带原仓库的 Actions 运行、产物、旧 PR 或提交身份。公开候选可以先在本机准备，不会自动上传。

若选择公开原仓库，需要先决定邮箱等身份信息是否可公开；若不可以，则另行制定备份、全引用历史清理、PR/平台记录处理和检查方案。该操作会改变提交标识并影响两个本机工作区和现有 PR，不能作为普通修复直接强推。

仓库公开后，原 APK 仍是手动覆盖更新。真正的在线更新还需要单独发布清单、签名安装包、对应源码和下载校验，不因仓库可见性改变而自动可用。

## 重复执行审计

先从 [Gitleaks 官方发布页](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1) 获取并验证工具。报告可放入忽略目录：

```powershell
python scripts/audit_publication.py --repo . --gitleaks C:/tools/gitleaks.exe --output artifacts/publication-audit.json --require-public
# 只检查一个已提交源码快照，不表示旧历史已清理：
python scripts/audit_publication.py --repo . --snapshot --gitleaks C:/tools/gitleaks.exe --output artifacts/snapshot-audit.json --require-public
```

脚本复用 Gitleaks 扫描密钥，另外检查提交身份、受限路径、LAN/设备标识和私人目录。`--metadata` 可接收本机保存的 GitHub API 清单；其中元数据通过不等于日志和附件内容通过。报告只保存计数/位置，不包含秘密值和私人邮箱原文。

未来每个大阶段按范围审计一次，分清公开阻断、已复现数据问题和低风险维护项。新增需求先做架构适配检查，再决定是否需要模块调整。
