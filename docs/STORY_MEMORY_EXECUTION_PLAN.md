## 1. 用户目标与本轮纠正

目标项目：T-companion。借鉴和按授权复用 SullyOS 的聊天、记忆与见面中的剧情能力，形成文件职责明确、同一功能集中实现的系统。

### 1.1 已确认的需求

| 编号 | 用户要求 | 对执行的约束 |
|---|---|---|
| U01 | 当前先做审计与方案；实施需要之后明确要求 | 本轮只写文档及文档读取入口，不改运行代码、不构建、不发布 |
| U02 | 见面只需要剧情，不需要原来的陪伴模式 | 不新增 SullyOS 的原见面陪伴页面；不据此删除 T-companion 已有世界对话 |
| U03 | 虚构剧情本来孤立，之后可以选择继续孤立或进入记忆 | 虚构剧场默认不自动写回；提供后续明确转入操作，不能把独立剧情做成永久封闭空间 |
| U04 | 当前记忆与 SullyOS 差别很大；关注宫殿、日/月总结和认知消化 | 记忆深度是核心目标，不只交付 BM25 分类界面或名册标签 |
| U05 | 消息也先生成一段角色当时的故事/情景 | 模型表达空间包含处境、动作和对手机消息的处理，不只输出聊天口吻 |
| U06 | 消息界面只显示实际文字消息，背后情景点击角色头像查看 | 叙事与手机消息独立投影，不把旁白混成对方发来的文字 |
| U07 | 角色忙、未玩手机时可以不回应；模型仍可输出情景 | 无回复是正常业务结果，不能用报错、空消息气泡或强制自动重试替代 |
| U08 | 同一功能集中实现，不嵌套、不冗杂 | 消息、记忆、模型传输、认知、持久化各有唯一所有者；UI 不复制规则 |
| U09 | 把讨论整理成可供后续执行阅读的文档 | 需求、疑问、设计假设和实施状态必须持续记录 |
| U10 | 原来的三种剧情记忆组合有价值，主要缺口是虚构剧情也能选择进入记忆 | 保留读取/写回的原有组合，追加手动转入；不强制把所有剧情都设成完全隔离 |
| U11 | 聊天消息应与世界里的实际情况对应 | 共享同一份已接受活动状态，通过明确接口协作；不能为了文件独立而各编一份生活 |
| U12 | 希望 AI 像人一样生活，获得持续的生活感和现实感 | 产品核心是持续处境、选择、行动、反馈和记忆；聊天/剧情/卡片是交互出口，不能只靠丰富话术或增加动作数量达成 |

用户关于 U03 的原话：

> 这个剧情本来是孤立的。但是，我们可以去选择，让它继续孤立，或者进入到记忆里。

用户关于 U05–U07 的意思：模型写角色当时的情景；实际发出的消息才出现在聊天里。没有发消息，也可以完成一次情景生成。背后情景从头像入口查看。

### 1.2 撤回之前助手的过早定案

- 不再把“带入角色原有记忆／新剧情自动计入主线／剧情归档”三个设置当作用户已经认可的产品模型。
- “之后转入记忆”不是“创建时必须选择自动写回”。最新讨论认可原有三种组合的价值；真实时间模式保留自动进入记忆，虚构剧场增加事后选择转入，见第 3.1 节。
- “进入角色记忆”不自动等于“改写人物身份”或“宣布整个故事为主线事实”。转入后的经历性质需要明确，见第 12 节。
- 不再把认知消化等同于已有“自我”。已有自我主要分析名册；消化需要消费实际经历并保存变化。
- 不以增加表情、随机延迟或强制长文来代替角色处境和回应选择。

## 3. 剧情：保留原有组合，虚构剧情可选择转入

### 3.1 最新模式方向

用户最新认可此前 SullyOS 三种组合的区分，下面将其保留为产品方案方向，并追加手动转入：

| 模式/设置 | 读取角色原记忆 | 自动进入角色正常记忆 | 用户事后选择转入 |
|---|---|---|---|
| 真实时间模式（原名“真实时间陪伴”） | 开启 | 开启，经过正常来源与整理流程 | 已进入部分去重，不再重复导入 |
| 虚构剧场，关闭记忆输入 | 关闭 | 关闭 | 支持，用户选段或摘要及接收者 |
| 虚构剧场，开启记忆输入 | 开启 | 关闭 | 支持，用户选段或摘要及接收者 |

“不需要原来的陪伴”指不新增原见面陪伴页面。保留剧情内部的真实时间/记忆组合，不等于重新增加一个陪伴 App；界面名称尚可调整。

两种虚构剧场的区别在记忆输入，均可继续独立或事后选择转入。转入一段不会开启未来自动写回，也不迁移整个剧情，不把独立故事改成持续世界的当前事实。

真实时间模式如果允许模型提出改变持续世界的行动，也必须经过第 5 节的同一世界规则。写入主记忆不能绕过世界校验，剧情正文中的虚构日期不覆盖持续世界的时钟。

### 3.2 虚构剧情的用户操作

1. 创建或继续虚构剧情，正文和进度保存在该剧情自己的时间线。
2. 不执行转入操作时，剧情内容继续独立，不被人物主记忆、日常总结或认知消化自动读取。开启记忆输入仅允许读取角色原记忆，不反向写回。
3. 用户之后选择一段剧情或一份事件摘要，预览接收角色及拟保存内容，确认转入角色记忆。
4. 转入成功后保留来源、接收者和回执；原剧情仍可继续，不需要整体切换模式。

“整段全部导入”可以作为范围选择，但不能把“单次选段转入”自动升级成“未来所有剧情自动写入”。

### 3.3 三种流转操作的状态

| 操作 | 状态 | 语义 |
|---|---|---|
| 保持独立 | 已确认 | 剧情只在自身范围内使用 |
| 选择内容转入角色记忆 | 已确认方向 | 通过统一 MemoryModule 保存，不复制整条剧情到聊天历史 |
| 发送剧情卡片给角色 | 用户提出的候选方向 | 在聊天中阅读讨论；与长期记忆转入是独立操作 |

转入记忆不自动授予其他角色知情权。剧情中的用户扮演身份与现实用户身份分开保存，指代不能重绑。

单次转入以“来源剧情 + 来源版本/区间 + 接收人物 + 操作标识”去重。源内容发生变化则要求重新预览，重试不重复记忆。转入后源被重写/删除时的处理策略列为待定，不能静默改写用户已经确认的记忆。

卡片如实现，应保存选定版本的有限文本快照和来源引用；定义后续源重写、删除及访问范围变化时的展示规则。选择“仅分享”时，自动记忆不能把故事变成亲历事件；人物可以记得用户分享过故事。

### 3.4 必须分开的三个维度

- 时间线归属：这段原文在哪里发生和保存。
- 记忆输入：依三种组合决定是否读取角色已有记忆；界面可使用上述预设，无需强迫用户配置所有底层字段。
- 记忆输出：真实时间模式经正常流程进入；虚构剧场只把用户选定的内容明确转入指定人物记忆。

后续 UI 可以简化这些操作，但底层不能用一个“隔离/非隔离”布尔值代替全部语义。

## 4. 线上消息：情景生成与外发消息分开

### 4.1 目标体验

用户发来一条消息。角色此刻可能在做饭、写东西、休息，可能没有看手机，也可能看到了但选择暂不回复。模型描写这段情景，并提出是否外发消息。

聊天窗口：只出现用户已发送消息和角色实际发出的文字。无回复时没有占位的角色气泡。

头像入口：展示已保存的背后情景及对应时间。打开入口只是读取，不请求模型、不改变角色当时的行为、不重新生成理由。现有头像菜单的进入方式在 UI 阶段明确，不能无意移除形象管理入口。

### 4.2 同一时刻的示例（合成场景，不是人物设定）

用户消息：“现在方便聊聊吗？”

背后情景：“他刚把锅端到灶边，手机留在外间。此时他尚未看到这条消息。”

外发消息：无。阅读状态：未读。处理结果：本次情景已完成。

之后有实际触发时，可以继续此情景：他查看手机，决定回复“刚才在做饭，现在好了。”这条文字才进入聊天。是否提供自动触发见第 12 节。

### 4.3 正常不回复与失败分开

| 情况 | 处理 |
|---|---|
| 有有效情景，选择不回复 | 正常完成，外发消息为零 |
| 看过消息，但选择暂不回复 | 正常完成，阅读与外发分别记录 |
| 情景生成超时、格式错误或内容为空 | 生成失败，不伪装为角色沉默 |
| 结构完整但保存失败 | 未提交，不发布消息、情景或阅读变化 |
| 只得到部分结构化输出后取消 | 不提交为完成情景，不标记已读；诊断中可保留失败状态 |

不能在协议层强迫每次生成一条 assistant 消息，也不能把不回复改写成“我现在不想回复你”后强制发出去。不要用随机已读不回概率替代角色依据，也不增加用于刺激用户的倒计时或固定回复承诺。

### 4.4 输出建议（实施前验证，非已定协议）

一次请求返回结构化生成结果，包含：

- `narrative`：用户可查看的场景正文，是创作内容，不是模型的内部推理或思维链。
- `observed_message_ids`：本次角色实际看到的消息。
- `delivery`：`send`、`no_reply` 或待定的 `defer`。
- `outbound_messages`：实际准备发送的文字数组，允许为空。
- `state_proposal`：有限的活动状态变化，包含时间与依据。

程序验证模式、来源、阅读顺序、内容长度、状态允许值和因果关系后，经同一事务接受。未通过验证的叙事不能覆盖世界或生活状态。

首版优先验证单请求同时生成情景与外发文字，避免“先生成故事，再另调模型把故事改成消息”的双份计费与语义漂移。解析属于同一消息生成模块，不在头像 UI 再实现一次。

流式数据先作为生成预览；角色消息在协议验证和保存完成后才视为已发送。是否允许经过验证的逐条发送，需要定义部分成功语义后再实施；不能用临时切片的 JSON 当已发送消息。

## 5. 知情、持续状态与生活模块的关系

### 5.1 两种查看权限

用户点击头像可看到背后情景，不代表用户在故事里目睹了情景，也不代表角色知道用户看过。角色只知道自己实际看到的消息、已有记忆及合规观察。

如果角色没有看手机，情景作者可以看到待处理消息，角色表现却不能引用尚未阅读的具体内容。这个区别必须进入协议与验收，不能只靠“请自然一点”的提示。

### 5.2 活动状态有唯一所有者

当前居民生活/世界模块已有计划与行动。线上情景读取其可用状态；与现有已提交活动、地点或身份冲突的候选不能直接接受。

已有世界绑定人物的活动变更经过原生活/世界规则；没有世界绑定的角色可以先保存有限的线上活动状态，由同一活动状态入口管理。不要让聊天模块、世界模块和另一个“生活模拟器”分别维护相互矛盾的位置、忙闲和时间。

具体适配时先检查真实需要扩展的状态，不为了每段描述强制创建地图、地点或世界事件。普通叙事可作为带来源的模拟情景记录；只有通过程序接受的活动变化才成为该模拟世界的状态。

世界里的“实际”指程序已经接受并保存的模拟状态，不表示真实设备环境感知。例如已保存“在书桌写作”，聊天不能另外生成“正在厨房做饭”并把它当同期事实；可以提出去厨房的行动，由世界规则接受后再继续。

### 5.3 模块集中与模块协作同时成立

集中的是数据写入权与规则实现，不是把所有功能放进一个文件。模块可以通过少量接口联系，不直接修改对方内部数据。

| 信息 | 唯一所有者 | 其他模块如何使用 |
|---|---|---|
| 当前地点、活动、模拟时间、已发生行动 | 现有世界/生活模块 | 聊天读取人物可用快照；变更以受限行动候选提交 |
| 手机消息送达、实际阅读、外发文字、待处理消息 | 对话模块 | 世界提供处境；记忆通过已接受消息来源读取 |
| 人物长期经历与召回 | 记忆模块 | 聊天/剧情/认知通过范围明确的查询或命令使用 |
| 稳定理解、担忧与期盼的解读 | 认知模块 | 可影响后续决策，不直接改写世界状态或名册 |
| 虚构剧情时间、场景、进度 | 剧情模块 | 与持续世界分区；记忆转入不把故事地点同步成当前地点 |

模型传输、事务、日志继续复用现有基础能力。不要在聊天侧重新实现生活模拟，也不要把消息、记忆和认知全部塞入 world-core。

建议协作过程：

1. 对话编排读取人物当前世界快照、版本及其可知内容，再读取自己的手机消息状态和合规记忆。
2. 模型据此提出情景、是否查看手机、是否回复及有限行动，不直接改数据库。
3. 编排在原事务中核对世界版本和消息状态，调用各所有者的规则验证候选，保存通过的状态与消息。
4. 生成期间世界已经变化时，过时的行动候选不得覆盖新状态；重新准备或提示冲突，不无限自动重发模型请求。
5. 记忆与消化只读取提交后的来源，界面读取相同已保存结果。

阅读消息的事实由对话模块写入；是否具备查看手机的处境由世界快照与共同接受规则约束。同一事务可调用多个模块的纯验证/修改函数，由一个编排入口提交；各模块不互相启动嵌套事务或模型请求。后续记忆整理可独立执行，不把网络调用放进事务。

首版使用明确函数与命令协作，不为这种联系额外引入全局事件总线或复杂消息队列。需要延后任务时再使用现有调度入口。

### 5.4 “稍后回复”是可恢复任务

首个闭环可以支持本次不回复，不依赖后台定时。未来如支持延后：

- 保存人物、会话、待处理消息集合、触发条件、状态版本与稳定任务标识。
- 实际触发时重新读取当前活动和新消息，不能直接发送过时生成结果。
- 使用现有居民调度/WorkManager 的能力和预算，不在聊天页新增常驻计时器。
- 人物暂停、会话删除、切换数据源、进程重启与已完成回复都必须能取消或去重。
- 不把“准备稍后回复”当成已创建任务；不把系统延迟当成角色主动选择。
- 不承诺关闭网页或 Android 强制停止后准点运行，也不补演过去并冒充当时已经发生。

## 6. 记忆与认知目标

| 数据职责 | 内容与规则 |
|---|---|
| 原始来源 | 聊天、剧情原文、已接受的背后情景与世界事件；区分来源类型和知情范围 |
| 经历记忆 | 有来源的具体陈述、经历、约定与解读；沿用原记忆条目和验证 |
| 日/月回顾 | 某段时间的回顾及精炼，标注范围；从原文/可追溯材料生成，不建立第二套独立经历库 |
| 稳定认知 | 对自己、用户、关系和能力的可修订认识，带依据、版本与人工保护 |
| 认知消化 | 回看合规经历，提出担忧/期盼状态变化与稳定认识，保存输入、变化和结果报告 |

宫殿是记忆分类、组织与查看方式；“自我”展示稳定认知、其依据与变化过程。界面分入口，领域逻辑共用。

Canonical 身份与后天解读分开。认知消化不自动覆盖 Canon/Persona，不把模型推测当用户提供的事实。SullyOS 的房间分类、门牌和状态机制可以借鉴，具体数量和标签属于设计选择，未获用户逐项确认。

来源资格必须明确：

- 角色未读的用户消息不是该角色已经知道的经历。
- 没有发出手机消息，不妨碍已接受的角色自身情景成为其经历来源。
- 不直接把整段作者旁白当事实；区分角色行动、主观感受、叙事推测与他人内心。
- 用户能查看一段情景，不使其自动成为双方共同经历。
- 虚构剧场不参加人物主记忆消化；用户转入后才按目标范围使用。真实时间模式按正常主记忆流程处理。
- 消化只消费已提交且有资格的来源；失败不推进处理进度，重试不重复形成认知。

需要扩展当前“完成问答 → 两条消息可提取”的来源约定，让没有 assistant 手机消息的成功情景也能被正确处理。

## 7. 模块职责与接口建议

继续使用扁平文件布局。以下为目标职责，文件名可在实施时结合实际规模调整；迁出逻辑后删除原实现，保留兼容转发即可。

| 位置 | 唯一职责 |
|---|---|
| `local-service.js` | 模块装配、接口路由、现有统一事务接入 |
| `conversation.js`（从现有实现迁出） | 生成任务、协议解析、消息状态、取消重试、实际投递与恢复；允许零条外发消息 |
| `context-builder.js`（从原函数迁出） | 身份、知情历史、活动快照、剧情/记忆材料及模式策略的唯一组装入口 |
| `story-core.js` / `story-service.js` | 剧情配置、进度、时间线及流转命令；复用对话和记忆模块 |
| `story-ui.js` | 剧情列表、阅读、选段与操作，不直接写共享数据 |
| 现有生活/世界模块 | 活动状态与允许变更的所有者；提供情景使用的快照与接受入口 |
| 现有 memory 系列 | 记忆来源、整理、保存、范围、关联、召回与预算 |
| `cognition.js`（按规模新增） | 稳定认知与消化规则/状态；记忆模块持久化接入，自我 UI 只调用 |
| 现有聊天 UI + 必要的头像情景面板 | 外发文字投影和情景只读投影；共用已保存生成结果 |
| 原存储/网络适配 | IndexedDB/SQLite、Keystore、原生网络、CAS/租约与恢复 |

建议的小接口：

- `conversation.process(sessionId, input, requestId)`：返回正常处理结果，`sent_message_ids` 可以为空。
- `conversation.getSituation(characterId, cursor)`：只读已保存情景，不联网生成。
- `story.transferToMemory(storyId, selection, recipients, sourceRevision, operationId)`：来源校验、预览后确认、去重及回执。
- `memory.recall(owner, scope, query, budget)`：一个入口执行人物/剧情范围限制。
- `cognition.digest(owner, scope, sourceRange, operationId)`：消费合规材料、提交变化与报告。

这些是领域接口，不是要求把本机全部改成 HTTP 服务。预览与实际发送共用 context-builder；任何 UI 不直接修改 `service.data` 或调用 `persist()`。

## 8. 数据与迁移建议

新增概念优先放入同一业务文档，复用现有消息和记忆实体。名称为建议，不是已实现字段。

| 实体 | 建议内容 |
|---|---|
| Generation/Turn | request_id、模式、输入来源、状态、情景引用、零到多条实际外发消息引用；允许 assistant_id 为空的明确新约定 |

| Delivery/Read | 到达、角色已读、外发是独立状态；已读只能引用已存在且属于该会话的消息 |
| Story | 独立时间线、配置、会话、原文引用、归档与版本 |
| TransferReceipt | 来源区间/版本、目标人物、生成记忆 ID、操作标识与来源性质 |

| Cognition/DigestReport | 认知条目、经历依据、状态变化、人工保护、消费进度及结果报告 |

旧备份的 completed turn 要求完整问答，不能不改验证就塞入“零回复成功”。建议显式升级备份/业务文档版本，读取旧版后在副本上迁移，旧消息与 ID 保留；新版本由旧客户端明确拒绝，防止静默丢字段。

流式临时输出、已接受情景、已发送消息和索引分别管理，只有业务事务成功才发布。OB 缓存保持可重建，不成为第二个记忆底账。

## 9. 分阶段执行与依赖

以下为建议顺序，实施须在用户明确授权后开始；任务尚未完成。

| 阶段 | 内容 | 阶段出口 |
|---|---|---|
| A：接口和兼容底座 | 明确 online/world/story、生成与消息分离、统一上下文、来源范围、迁移方案 | 原聊天/世界行为回归；零外发消息可以被模型协议和存储正确表达 |
| B：线上情景闭环 | 合成活动快照、结构化情景与 send/no_reply、头像只读查看、持久化和恢复 | 一次实际用户输入可生成情景而不发消息；失败与沉默区分 |
| C：剧情模式与记忆流转 | 保留三种记忆组合；单角色剧情、保存/继续/重写/归档、选段转入、预览与回执；卡片待语义确定 | 虚构剧情之后可选择进入人物记忆，不切换整条剧情模式；真实时间模式不绕过世界规则 |
| D：记忆分层 | 分类组织、日/月回顾、稳定认知和自我展示、跨来源资格与召回 | 不重复维护经历；来源和版本可回溯 |
| E：认知消化 | 从经历驱动认知及担忧/期盼状态，保存报告、去重、失败恢复 | 展示一次“经历 → 消化 → 认知变化”的完整可验证过程 |
| F：按需要增强 | 既有生活调度下的延后回复、多角色剧情、向量检索效果评估 | 不增加第二套调度、人物生活或记忆引擎 |

A 是 B/C 的共同前提；B/C 产生的合规经历进入 D/E。认知消化是目标交付项，不能用 F 的向量检索代替。文档不把全部产品功能绑定为一个大提交。

| 验收 | 明确断言 |

## 14. 世界书、预设、动作能力与持续生活

### 14.1 三者的职责

| 概念 | 解决什么问题 | 本项目的职责位置 |
|---|---|---|
| 世界书 | 可导入、组织、开关并按条件装配的提示词条目；内容可含背景、人物、文风、行为/互动规则、玩法和记忆提示等 | 上下文模块统一选择与装配；条目有作用范围，按内容性质区分设定与指令，不默认所有人物都知道其中的资料 |
| 预设 | 本次完整请求的组织、生成参数及提示布局；它也可承载文风、规则、玩法，与世界书在内容上重叠 | 同一上下文组装入口读取配置；模式协议和程序运行约束有明确优先级 |
| 动作能力 | 角色可以提出哪些程序操作、需要哪些参数，操作如何验证和反馈 | 集中登记动作描述/参数/路由，由消息、世界、记忆等原所有者执行规则 |

例子：世界书说明“书店二十点关门”，运行状态保存“现在十九点、人物在家”，预设要求依据当前处境表达并区分情景与外发文字，动作允许“移动到可达地点/联系已认识的人物”。模型可能决定先联系朋友再去书店，程序执行后才更新实际状态。

“世界书只提供背景资料”是之前助手过窄的解释，已撤回。世界书也可以通过提示影响行为、叙事和模拟状态；一些宿主扩展还能动态更新条目。T-companion 选择由世界模块维护当前坐标/活动、消息模块维护已读，这属于本项目的数据所有权设计，不是对世界书能力的普遍限制。世界书可以读取这些状态的投影，但不重复维护权威副本。

预设或世界书可以教模型生成动作请求；相应操作能否改变应用状态，取决于宿主的解析/执行能力。动作库也不是无限执行任意输出的解释器。所谓动作要区分“抬头、叹气”等叙事描写与“发送消息、转发卡片”等程序操作，前者不自动产生后者的效果。

### 14.3 持续生活的最小闭环

产品应连接：已接受世界状态与个人记忆 → 当前处境与有限计划 → 角色选择行动或等待 → 原领域规则执行 → 产生结果/观察 → 当事人形成经历 → 记忆与认知更新 → 下一次决策。

模型只负责提出选择和表达，程序保存持续状态、处理时间与执行结果。行为可以与用户当下消息无关；也允许什么都不做。动作变多不自动产生生活动机，需要明确人物此刻在做什么、为什么改变活动、结果是否影响下一步。

本项目已有居民生活、计划、任务预留/响应/接受及原生有限后台，后续在这套闭环上扩展消息与人物关系；不另建“世界生活”“聊天生活”“头像生活”三套循环。移动等确定性过程由规则推进，模型在有意义的决策点调用，不逐秒生成旁白。未实际执行的时间段不能打开界面后补写成已经发生的记录。

该目标不自动授权接入真实手机消息、第三方账号或现实设备。世界书和模拟生活状态也不等于摄像头/定位等设备观察；接入真实来源另按明确范围处理。

### 14.4 角色联系角色的候选设计

用户以“可以私聊其他角色”说明期望的互动自由度。作为后续候选能力，实施前核对阶段范围，不能把举例扩成全功能社交应用。

1. A 从自己的已知内容、当前活动和允许联系对象中决定联系 B。
2. 对话模块执行 send_message，保存真实发送者/接收者、消息和投递标识；不以 A 对用户的会话冒充 A/B 私聊。
3. B 是否看到消息取决于自己的可用状态；看到后仅使用 B 的身份、记忆、已知观察及收到的内容决定回复或不回。
4. 不由 A 的一次生成代写 B 的已接受决策；B 的响应使用 B 的上下文和既有任务执行流程。
5. 只有实际收到/观察到的人物获得对应来源。转发卡片只携带选定且允许分享的内容，不附带发送者整个记忆库。
6. 每次互动有有限轮数/请求预算、去重与取消规则，避免两个自动角色无限互相触发；暂停后任务停止，已发送消息保留。

动作登记集中保存“操作名、参数、适用模式、执行入口”。例如角色私聊与给用户发消息都调用同一消息领域，转发也复用原消息/卡片投递；不同 UI 不再实现另一套收件箱。第一版仅暴露该阶段已实现的动作，不先造一个包含全部未来功能的大型动作库。

### 14.5 对实施计划的补充

- A 阶段的统一上下文，为世界书、模式预设和活动快照保留清楚职责；动作说明与当前真正启用的操作一致。
- B 阶段必须接已有生活状态；接受角色等待或沉默，验证一次生活状态变化如何影响线上回应。
- D/E 阶段验证“行动与反馈 → 经历 → 消化 → 后续选择”的来源链，避免认知只作展示标签。
- F 阶段的角色互联先验证一对人物、一个消息入口、有限往返，不直接展开朋友圈/商城等无关应用。
- 增加验收：未注册动作不执行；失败不能报告成功；同一动作重试不重复投递；B 不读取 A 私有记忆；只有转发范围内内容到达 B；暂停与预算会结束自动往返；世界书不能覆盖当前已保存活动。

### 14.6 社区分享的世界书：载体与内容分开理解

用户指出小红书有大量世界书分享，之前只解释成“背景资料库”与其使用体验不符。2026-10-31 查证 SillyTavern 官方文档：World Info 是动态插入提示的机制，条目可以承载希望放进提示的各种内容；官方用途也包括不同情境的系统提示、记忆与随机事件。不能用“背景知识／生成规则”硬划世界书和预设。

社区常见用途应按内容理解：文风要求、减少重复表达、慢节奏关系发展、多人物互动、剧情与事件规则、状态面板输出、记忆回顾提示、背景和人物补充等。这些是可承载的用途举例，不代表已逐一核对用户所见的小红书分享，也不保证任一模型按要求实现。

区别主要在装配：世界书常将内容分成条目，配置作用对象、触发和插入位置；预设常组织整份请求和参数。同一种文风或行为规则可被作者做成世界书，也可放入预设。名称不决定效果，需要查看条目正文、触发条件和宿主支持。

一个所谓“记忆世界书”可能只要求模型总结或回顾，也可能配合脚本和状态工具保存；不能仅凭名称认定它具有数据库记忆与召回。“转发/社交世界书”可教模型提出动作，真正投递仍需宿主执行。分享包如含正则、脚本、宏或特定应用格式，要分别核对依赖。

对 T-companion 的实施影响：允许统一的世界书条目库承载可组合的设定与规则，不为每一种导入文风新建业务模块；统一上下文入口负责选择和装配，原领域模块继续执行世界、消息和记忆操作。导入兼容性按条目结构、触发、位置、宏及扩展依赖逐项记录，不能只因 JSON 能读取就宣布完整兼容。

参考：[SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)、[SillyTavern Adding to the Prompt](https://docs.sillytavern.app/usage/prompts/#adding-to-the-prompt-world-info)。本次没有取得用户所指的具体小红书帖子或世界书文件，不对其具体作用下结论。

### 15.2 首项工作的交付边界

首项审计的产物是逐操作对照、对应文件和数据流、保留/扩展/替换决定，以及可独立验证的首批实施任务。还需逐函数核对选定上游模块的依赖、导入授权与目标数据兼容；不能把本节的使用说明对照写成整套迁移已经验证完成。

建议第一个实施小阶段为“统一记忆来源、归属与召回入口”：

1. 明确人物主记忆、虚构剧情，以及用户显式转入后的归属与来源版本。
2. 让现有聊天/世界经历继续经同一写入与召回入口；为后续剧情和零外发消息情景定义来源契约，暂不实现对应页面。
3. 验证未读消息不成为角色已知经历、独立剧情不越界、来源可追溯、失败不推进进度和旧数据保留。
4. 在此之后分小阶段接宫殿分层/日月回顾、认知消化及剧情转入，再推进线上情景消息和生活联动。

以上是当前建议的依赖顺序，不删减原有功能目标。借鉴 SullyOS 的用户操作与功能链，结合本机 Android 架构选模块；不机械搬整套全局状态，也不因为已有 OB 就拒绝评估上游具体记忆能力。
